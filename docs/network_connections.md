# Obsluha příchozích požadavků

Následná kapitola pojednává o navazování a obsluze příchozích spojení serverem.

## Smyčka obluhy příchozích spojení

Nejprve nastiňme základní smyčku obsluhy příchozích spoejní. Po spuštění samotného serveru reprezenovaného `HttpServer` objektem začne server poslouchta a přijmat TCP spojení na portu specifikovaném při inicializaci tohoto objektu. Poté co je úspešně navázano TCP spojení s klientem, server zahájí smyčku komunikace prostřednictvím HTTP. To v praxi znamená, že po úspešném navázaní spojení začne jeho prostřednictvím přijmat data od klienta, která se pokusí interpretovat jako HTTP požadavek. Pokud jsou obdržená data validním HTTP požadavkem, pokusí se ho server obsloužit, v opačném případě odpoví chybou a spojení ukončí.

Samotný process obsloužení požadavku se pak sestává z nalazení správného handleru pro jeho obsloužení, pomocí routovací tabulky serveru, která jednoduše mapuje handlery na konkrétní endpointy (pokud server v routovací tabulce nenalezne vyhovující záznam, pak použije defaultní handler, který typycky pouze vrátí HTTP 404). Následně server zavolá nalezený handler, kterému předá reference na přijatý požadavek a objekt reprezentující HTTP odpověď, po jeho dokončení pak jednoduše serializuje data uložená handlerem do objektu odpovědi a odešle je jako odpověď klientovy, čímž je požadavek obsloužen. V případě, že volaný handler při obsluze požadavku z jakáhokoliv důvodu selže, pak se server postrá o automatické ošetření této chyby. Toto o šetření spočívá v zalogování nastalé chyby a odeslání HTTP odpevědi s odpovídajícím HTTP statusem klientovy a následném korektním zavření spojení. Obdobný mechanismus je kromě izolace nenadálých chyb při vykonávání handlerů používan také pro mechanismus reportování chyby očekávaných chyb z handleru (například nesprávná metoda příchozího požadavku), který bude popsán v dalších kapitolách. Jedná se tedy o klasickou komunikaci request respone, kdy jedno spojení odpovídá jednomu požadavku klienta, tak jak jí definuje HTTP 1.1.

Další obsluha spojení ze strany serveru pak závisí na nastavení halviček obsluhovaného požadavku, pokud klient odešle požadavek s hlavičkou `Connection:Keep-Alive`, pak server po jeho obsloužení zahájí komunikační smyčku, kdy ponechá spojení otevřené a čeká na další příchozí požadavek,který obslouží stejným způsobem, v opačném případě spojení s klientem jednoduše ukončí a klient tak pro odeslání dalšího požadavku musí nejprve znovunavázat spojení se serverem. Samotný web server implementovaný v rámci projektu pak automaticky nastavuje hlavičku `Connection:Keep-Alive` pro všeny odpovědi na dotazy (kromě odpovědí s chybovým HTTP statusem) ve snaze vynutit znovupoužívání navázaných spojejí ze strany a zlepšení celkového výkonu vlivem menšího overheadu navazování nových spojení.

## Paralelizace

Nyní, když již máme základní model obsluhy příchozích spojení, můžeme se přesunout k jeho pralelizaci pro dosažení lepších výsledků po stránce výkonu. Asi nejednodušším modelem paralelizace HTTP serveru je pro každé příchozí spojení alokovat nové vlákno, které bude sloužit pro jeho obsluhu. Jak je již patrné z předchozí kapitoly, tento model ale není úplně vhodný, protože jak již bylo zmíněno HTTP/1.0 defaultně otevírá nové spojení pro každý požadavek, z čehož plyne že tento model by byl vlivem overheadu pro vytváření a spoštění nových vláken velmi neefektivní.

Možným vylepšením tohoto modelu je využití thread poolu předem připravených worker thredů, kdy by se pro obsluhu nově příchozího spojení namísto nově vytvořeného vlákna využilo volné vlákno z thread poolu a po uzavření spojení by do něj bylo opět navráceno. Tento model již odstraňuje problém s overheadem alokace nových vláken, pro účely thoto projektu jsem se ho však rozhodl odplňit ještě o asynchroní práci se spojením v rámci jednoho vlákna.

Tento model využívá architektury, která je doporučena i v rámci oficiálni dokumentace knihovny ASIO. Tedy využít run loop `io_context` poskytovaný knihovou ASIO a následně na něj dispatchovat jednotlivé operace v podobě asynchroních callbacků. Jak již bylo řečeno v rámci projektu je využívano asynchroní zracovaní požadavku doplněné o jednoduchý thread pool. Hlavním smyslem tohoto threadu poolu je umožnit vykonávání callbacků zpracovávaných run loopem nejen konkurentně, ale také pralelně. Všechna vlákna thread poolu tedy pouze vykonávají zpracování úloh jednoho globálního run loop na nějž jsou dispatchovány požadavky z celé aplikace. Pro zachovanírozumného chování jednotlivých callbacků při kombinaci konkurence a paralelismu je třeba zajistit, aby byl každý callback vykonáván pouze na jednom vlákně současně, což zajištuje knihovní `asio::strand` exector používaný při dispatchování jednotlivých callbacků. Díky tomuto způsobu vykonávání pak lze o jednotlivých callbacích uvažovat v sémantice sekvenčního vykonávání a však není jím zajištěna thread safety globálního stavu sdíleného mezi více spojeními (různé callbacky se stále spouští konkurenče, jinak by celý model postrádal smysl). Jediným takovýmto globálním stavem je v současné chvíli routovací tabulka serveru, ke které ale současný návrh api neumožňuje přistupovat jinak než prostřednictvím konfiguračních metod `HttpServer` objektu, o kterých se nepředpokládá, že budou volány mimo fázy konfigurace před samotným spuštěním serveru a tedy není bezpečné je volat v konkurenčním prostředí.

Samotné spojení a asychroní operace nad ním jsou zapouzdřeny pomocí objektu `Connection`, který představuje jedno síťové spojení a dědí z `std::enable_shared_from_this`, což umožňuje získat `shared_ptr` na daný `Connection` objekt uvnitř jeho metod zapouzdřujících jednotlivé asynchroní operace. Předání takto získaného `shared_ptr` do asynchroního callbacku pak zajišťuje dostatečnou životnost `Connection` objektu, nato aby run loop mohl vykonat všechny nad ním dispatchované operace.

Tento model asi není nejběžnější implemwentací zpracování požadavků pomocí multithreadingu, avšak jak bylo popsáno výše, jedná se o po stránce výkonu lepší řešení něžli představuje naivní thread per request řešení, nebo běžný thread pool. Zároveň se také jedná o model doporučený při práci s používanou knihovnou asio.

## Automatické přesměrování HTTP na HTTPS

Server nyní defaultně vynucuje komunikaci výhradně prostřednictvím HTTPS. To v praxi znamená, že server již při navazování spojení s klientem analyzuje příchozí data a pokud neodpovídají formátu jenž má TLS handshake, odešle zpět přes již navázané TCP spojení odpoveď v podobě klasického HTTP redirection (tedy odpověď s HTTP status `301 Moved Premanently` a hlavičkou `Location` nastavenou na stejný cíl, ale s `https` schématem) na spojení používajíci HTTPS. Toto přesměrovavání tedy funguje pouze tak, že server se pokuší na HTTPS přesměrovat HTTP požadavky, které přichází na port na němž poslouchá. Pro přesměrovávání HTTP provozu na HTTPS z jiného portu (typycky automatické přesměrovávání http://host_domain.com nad https://host_domain.com) je nejednodušším řešením spuštění pararelně druhé serverové instance, která na veškeré dotazy odpovídá HTTP přesměrováním na hlavní server obsluhující HTTPS provoz.

Nyní, když jíž máme základní model zpracovaní příchozích spojení, se mužeme přesunout k implementaci samotného HTTP protokolu, která je zcela nezbytnou součástí jejich obsluhy a zabývá se jí následující kapitola.
